### 1.1 核心定位（一句话介绍）

**把电竞直播弹幕，变成可溯源、可支持决策的情报，并且越攒越值钱。**

**我们做什么**：多路直播间（虎牙 / SOOP / KICK）的弹幕，按比赛节点加工成
结构化情报——赛前共识、BP 后、局中、局末、赛后复盘；事实层用官方数据
（Riot / Liquipedia / HLTV / Polymarket 结算）校准，弹幕只负责提供"观众
怎么看、有什么信号"。

**给用户带来的价值**：

- 决策者（付费）：赛前 BP 到局中，1-2 分钟拿到别人刷几个小时弹幕也整理不出的
  东西——灰信号、BP 锚点、观众共识、盘口讨论，每条可溯源、可验证；
- 普通观众（免费）：赛后复盘 + 验证闭环（当时怎么说、后来准不准）+ 知识摘要，
  看懂比赛、看懂共识；
- 长期资产：选手 / 队伍 / 英雄 / 联赛四个维度的知识越攒越厚，形成复利情报库——
  这是别人零散经验、我们系统性积累的差异化。

> 与产品框架文档（docs/task/INTEL_PRODUCT_FRAMEWORK_2026-08-31.md 第 0 节）口径一致；
> 本 PRD 全部设计以实现该定位为目标。

## 2. 背景与目标

### 2.1 背景

弹幕情报库已在线下/线上跑通全链路（2026-08-18 起）：虎牙/SOOP/KICK 多直播间弹幕
采集 → 按比赛×节点时间窗切片 → 规则层统计（词表/提及量/密度/灰信号）→ LLM 提炼
（固定提示词直连 DeepSeek API）→ 门禁校验 → HTML/MD 双格式发布 → 订阅付费墙。

现状问题：

1. 代码散落在本地项目与 VPS 脚本目录，未形成标准 Python 工程（模块边界、配置、
   依赖、测试、文档不完整）；
2. 生成路径历史上有 12 段/10 段多套模板并存，需收敛到唯一标准（旧 10 段框架）；
3. 情报混淆、时效滞后、价值下降、格式混乱四类失效模式需在架构层面根除；
4. 成本与质量不稳定，需程序化固化（提示词、门禁、SLA 指标）。

### 2.2 目标

1. 把弹幕情报库做成**可部署、可维护、可回归的标准 Python 项目**；
2. 全链路自动化：比赛开始 → 采集 → 节点触发 → 快报 → 完整版 → 发布 → 结束复盘 →
   情报库沉淀 → 验证回填，无需人工干预；
3. 输出质量稳定：结构唯一（旧 10 段框架）、事实层只信官方、弹幕结论可溯源、
   缺数据显式标「无」；
4. 成本可控：单页 LLM 成本 ≈ 0.04-0.06 元，一场 BO3 ≈ 0.25-0.45 元；
5. 满足 SLA：快报 ≤2 分钟、完整版 ≤10 分钟、赛后复盘 ≤15 分钟（北京时间）。

### 2.3 非目标（明确不做）

- 不做 Dota2 / Valorant 采集（预留扩展位，不投入）；
- 不恢复 Twitch 自动采集（用户决定暂停；除非明确恢复）；
- 不做弹幕意见自动聚类（2026-08-26 已回滚弃用）；
- 不做「速览卡/方向板」12 段模板（已回归旧 10 段框架）；
- 不在本项目内持有私钥或执行真实下单（交易另属 polydata 仓库）。

## 5. 功能需求（详细）

### 5.1 采集层（capture）

**需求 FR-CAP-1：多直播间采集**

- 数据源：虎牙（官方流/957/毛毛/米勒/硕硕等）、SOOP（LCK CL）、KICK（CS2）；
- 每个直播间一个采集任务，独立落盘、独立健康状态、异常自动重启；
- 会话维度：同一场比赛的所有直播间必须放入同一 session（intel.json 聚合），
  禁止按平台拆 session；
- 完整性：每场情报必须标注「实际数据源 / 预期数据源 / 缺口」；离线房间标注
  「离线未采」，禁止静默缺源。

**验收标准**：比赛开播后 1 分钟内开始采集；断线自动重连 ≤60s；任一房间数据
中断有日志与 TG 告警；采集元数据（房间、起止时间、条数、缺口）落盘。

**需求 FR-CAP-2：直播间注册表**

- `config/streamers.json`：房间 ID、平台、联赛归属、启用开关、备注；
- 联赛默认采集集 `config/leagues.json`：LCK / LCK CL / LPL / LEC / CS2 各指定
  默认房间集（isOn 标记）；
- 新增/停用房间改配置即可，不重启整个服务。

**验收标准**：修改配置后热生效；同一房间（如 maxixi 与 CSBOY 官方房重叠）
自动去重，不重复采集。

### 5.2 切片层（slice）

**需求 FR-SLC-1：节点时间窗切片**

- 节点定义：赛前（PRE）、BP 后（BP）、局中（MID）、局末（END）、整场（FULL）；
- 切片起点 = 本节点阶段起点（官方 schedule + 弹幕密度突变校准确认）；
- 禁止混入上一局尾段、局间闲聊、更早节点数据；
- 整场复盘切片 = 全窗口等距抽样（不只喂尾部）；
- 联赛源硬隔离：切片前按 league_files 过滤，CS2 只进 CS 直播间弹幕，
  LoL 各联赛只进对应联赛直播间；混源整场作废（void_match_intel）。

**验收标准**：每个切片文件带窗口起止时间（UTC 与北京时间）；节点边界与官方
schedule 一致；跨联赛混源为 0（回归测试锁定）。

### 5.3 规则统计层（rules）

**需求 FR-RUL-1：词表与提及统计**

- 词表：队伍（team_names.json）、选手、黑话双语映射（야필패=亚索必败）、
  联赛词、灰信号词；
- 统计输出：弹幕总数、活跃用户、密度（条/分）、队伍/选手提及量（正/负）、
  正负锚、群体共识主题、灰信号条数与样本；
- 词表维护：半自动（LLM 发现候选词 → 确认入表 → 回归测试），禁止全自动
  （防 OKBRO / bro tax 类玩梗误收）。

**验收标准**：规则层输出 JSON（intel.json）字段固定、可回归；漏词有测试告警；
灰信号只作聚合与风险标注，不作结论。

**需求 FR-RUL-2：密度时间线**

- 按分钟聚合弹幕条数，输出密度峰值（时间+条数+代表样本）；
- 事件反应识别：一血/团战/偷家等关键节点弹幕爆发，带时间戳与强度。

**验收标准**：密度时间线与真实弹幕时间戳一致，无编造/平移。

### 5.4 LLM 提炼层（refine）

**需求 FR-REF-1：固定提示词直连 DeepSeek**

- 程序组装固定提示词（prompts/report_full.md、report_game.md、report_pre.md、
  report_live.md）+ 规则层统计摘要 + 代表弹幕样本（≤60 条、每条 ≤50 字、
  带北京时间戳），直连 DeepSeek API；
- 模型 deepseek-chat、temperature 0.3、max_tokens 首调 8000/重试 16000、
  重试 ≤3 次；
- LLM 只当「打字员」：结构/标准/校验全在程序，换模型不影响质量。

**验收标准**：单页输入 ≈3.3k / 输出 ≈7.9k tokens，成本 ≈0.05 元/页；
每次调用记录 usage。

**需求 FR-REF-2：自由提炼与特殊情报保留**

- 群体共识用自由段落描述（不强制结构化卡片）；
- 主动保留规则统计覆盖不到的特殊情报（新梗、罕见指控、转折信号），不过度过滤；
- 价值单元双类：持续观点（队伍/选手/BP/盘口共识）+ 事件反应（关键节点爆发）；
- 每条结论带可信度字段：来源分层 + 置信 + 样本量 + 时间窗。

**验收标准**：页面信息密度不低于样页（intel_danmu_LCKCL-NS-DNSC_full_old_2026-08-31.html）；
无「有结构没内容」的章节。

### 5.5 校验门禁层（verify）

**需求 FR-VRF-1：结构门禁**

- 每段 `<h2><span class="no">N</span>标题</h2>` 必须恰好出现 1 次（缺段/重复段
  都判不过并重试）；
- 段落标题关键词按节点类型校验（A 型 0-10 / B 型 0-11 / 赛前 0-8）。

**需求 FR-VRF-2：事实层与结果门禁**

- match_state_guard 四道闸：时间门槛（已开始 ≥30 分钟才允许判结束）、
  结构源优先、反讽识别、比分源滞后；
- 结果判定优先级：Polymarket 结算 > 官方 API > 官方直播间标题 > 中文战报 > 弹幕；
- 弹幕禁止单独定胜负；「一波了/恭喜X」只作候选信号；
- 终局以 Polymarket 结算价为最终仲裁，多端不一致立即修正。

**需求 FR-VRF-3：来源与反编造门禁**

- 无中生有零容忍：无本场/前局/历史数据支撑的不写；
- 推测必须标注「推测·待验证」，与事实分离；
- 跨场话题（NiKo/Falcons、donk/Spirit）标注「跨场话题·不适用本场」；
- 时间线只用真实弹幕时间戳，禁止编造/换算/平移；
- 禁止无源编造胜率数字（预测/弹幕/估算胜率需带证据来源）。

### 5.6 输出层（render）

**需求 FR-RND-1：模板唯一标准**

- 唯一标准 = knowledge/INTEL_TEMPLATE_OLD_2026-08-31.md；
- A 型整场（0-10）：比赛信息 → 结果总览（弹幕口径·待回填）→ 逐局复盘（每局含阵容）
  → 队伍画像（引用 teams.json）→ 人员画像（带提及量）→ 灰信号汇总 → 联赛规律与版本
  → 预测验证（闭环）→ 盘口讨论（Polymarket 交叉）→ 情报含义与后续观察点（LONG/SHORT）
  → 数据与溯源（实际/预期/缺口）；
- B 型局中（0-11）：在 A 基础上加「状态核验/密度时间线/方向性情报」；
- 赛前（0-8）：比赛信息 → 赛前共识与状态核验 → 队伍画像 → 人员画像 → 灰信号 →
  联赛规律 → 盘口讨论（无则待开赛）→ 情报含义与观察点 → 数据与溯源；
- 无「核心情报速览」速览卡；speedcard_consistency 不再作为发布门禁；
- 方向表达只罗列证据（正锚/负锚/群体共识），不下「看好 X」结论。

**需求 FR-RND-2：快报与完整版同 URL 升级**

- BP 后/局中先出快报：规则直出硬统计（比分/提及量/灰信号数/密度），
  页面标注「速览版 · 完整版跟进」，1-2 分钟内上线；
- 完整版 ≤10 分钟跟进，同 URL 原地覆盖升级（不产生第二个页面）；
- 局末直接完整版。

**需求 FR-RND-3：双格式与镜像**

- HTML（站点展示，SAP/Apple 风格：#f5f5f7 浅底、白圆角卡片、#0071e3 强调色、
  系统字体栈、移动端优先）+ MD（入库核心）；
- MD 镜像必出，同步 knowledge/intel_pages/ 与 README 索引；
- 全页至少 3 个 `<details>` 折叠区（弹幕原文摘录/完整时间线/长画像）；
- 时间一律北京时间展示。

### 5.7 发布层（publish）

**需求 FR-PUB-1：站点生成**

- 页面类型：今日情报（赛程+节点进度+节点入口）、历史情报库、画像库、灰信号统计、
  验证闭环、订阅页；
- 今日页每场必须展示节点进度（未开始/进行中/已结束 + 已出节点）；
- 时间轴壳（match_<slug>.html）必须与节点页同步（禁止「页面上线但入口显示暂无」）；
- 比赛一结束，该场所有节点页自动转免费公开。

**需求 FR-PUB-2：付费墙**

- Pro = 进行中的节点页 + 完整画像；其余全公开；
- 付费墙注入按「比赛是否已结束」判定（settlements / 全小局 closed / 结果回填），
  禁止按文件名一刀切；
- 会员验证：TG 用户名/QQ 号 × 名单 × expires，本地 24h 缓存。

**需求 FR-PUB-3：发布前审计**

- 全站审计：导航唯一、无旧模板残留、Pro 页付费墙齐全、节点完整性、
  页面 × 联赛 × slug 关联一致、速览卡残留为 0；
- 审计不通过 = 不发布；
- 发布链路：VPS → 站点仓库 → GitHub Pages（或 nginx 直出），目标部署耗时 ≤1 分钟。

### 5.8 订阅层（subscribe）

**需求 FR-SUB-1：登记与试用**

- 订阅页登记表单（昵称/TG 或 QQ/想开通的档位/备注）→ 推送到站长 TG；
- 试用档：1 美元 3 天（统一付费试用）；7 天免费名额仅信任圈/推广；
- 会员名单：members.json（VPS 接口优先，可回退 Gist）；
- 到期前 TG 自动提醒（剩余 N 天），到期自动失效。

**验收标准**：登记 → 名单 → 解锁 → 到期全链路自动化；验证 API
（verify-member）实测通过；陌生人拒绝、订阅者解锁、Pro/免费分层正确。

### 5.9 情报库沉淀层（library · 知识资产）

> 定位：这不是"自动合并弹幕统计"，而是把每场比赛中出现的**有价值的情报**提炼成
> 长期知识资产，按 选手 / 队伍 / 英雄（地图）/ 联赛 四个维度持续积累，形成复利资产。
> 统计（提及量/密度/正负锚）只是底料；沉淀的是情报本身及其证据与验证。

**需求 FR-LIB-1：本场情报资产提炼（每场必做）**

- 每场比赛结束后，基于本场全部节点情报（弹幕共识、灰信号、BP 锚点、盘口讨论、
  事件反应、验证结果），由提炼层产出「本场情报资产」；
- 资产内容覆盖但不限于：选手英雄池/风格的新信号、队伍战术与 BP 倾向、
  英雄强度与 counter 共识、联赛规律与版本理解、灰信号及其兑现、观众黑话；
- 每条资产固定结构：
  `{主题, 维度(选手/队伍/英雄/联赛), 洞察一句话, 证据(时间+来源), 置信, 验证状态, 时间}`；
- 禁止把提及量/密度等原始统计直接当资产写入（统计只作佐证字段）。

**验收标准**：每场至少产出若干条可溯源资产；资产必须来自本场真实弹幕/官方数据，
无中生有为 0；与"数据带量"底线不冲突（每条资产可回看原始样本）。

**需求 FR-LIB-2：四维知识库（长期积累）**

| 维度 | 沉淀内容 |
| --- | --- |
| 选手 | 英雄池与招牌英雄、风格标签（激进/稳健）、状态趋势、关键表现/名场面、观众共识与黑话、BP 锚点（选手×英雄）、灰信号记录 |
| 队伍 | 战术体系与版本适应、BP 倾向（常用/禁用）、翻盘/顺风能力、选手组合、状态趋势、跨场战绩情报、灰信号记录 |
| 英雄/地图 | 英雄强度认知与版本理解、counter 关系、出场/胜率趋势、观众共识（如"亚索必败"黑话）、CS2 队伍×地图强图 |
| 联赛 | 联赛规律（晋级规则/节奏/版本环境）、强队格局、盘口习惯、季前/常规/季后赛特征 |

- 摘要免费展示（近况一句话 + 关键统计 + 验证数据），完整知识 Pro；
- 画像/知识页引用必须带时间，禁止用历史画像冒充本场数据；
- 新增维度（如 BP 组合、特定英雄池选手）以"新资产主题"方式追加，无需改表结构。

**需求 FR-LIB-3：沉淀引擎（幂等合并与趋势）**

- 幂等：同场不重复入库（runtime/accumulated_matches.json 防重复）；
- 合并规则：新资产追加；旧认知被新证据更新时保留时间与来源（"何时由谁更新"）；
  单源 = 待验证、多源共振 = 确认、方向背离 = 分歧（单独标注）；
- 趋势线：实体维度随比赛数延伸（选手英雄池扩展、队伍版本适应、英雄胜率走势、
  联赛格局变化），以时间轴展示；
- 验证回填：灰信号兑现率、BP 锚点应验率、预测命中率持续累加进实体知识，
  成为可查证的"长期口碑"；
- 闭环：每场沉淀 → 画像页更新 → 下一次比赛情报可引用（标注来源时间）。

**验收标准**：同一实体连续 5 场后出现可读的趋势/画像变化；沉淀幂等无重复；
画像页所有引用带时间与来源；跨场统计（灰信号兑现率/BP 锚点兑现率）可见。

### 6.2 成本预算

- LLM：单页 ≈0.04-0.06 元；一场 BO3（5-8 页）≈0.25-0.45 元；
- VPS：2C4G80G ≈ $18-24/月；
- 目标：每晚 5-6 场 ≈ 1.5-2.5 元 LLM 成本；
- 每页记录 usage 与成本，超阈值 TG 告警。

### 6.3 可用性与可靠性

- 采集、管线、发布分别由 systemd service/timer 托管，崩溃自动重启；
- 幂等：状态文件存在即跳过（节点不重复生成、沉淀不重复入库）；
- 数据端完备：缺源显式标注，禁止静默；
- 全链路日志：journald + runtime 日志，异常有堆栈与告警。

### 6.4 安全与合规

- 灰信号只作风险标注，对外永远写「观众质疑 · 非结论」；
- 弹幕引用脱敏，不展示用户身份；
- 服务条款一行「数据仅供参考」；
- DeepSeek API Key 只存服务器环境/配置文件（600 权限），不入库不提交；
- 不做违法事项；不持有私钥。

## 10. 流程设计（端到端）

### 10.1 比赛生命周期

```text
1. 每日清单同步（matches_today.json）→ 比赛进入今日页「未开始」
2. 开播检测（官方 schedule / 弹幕密度突变）→ 启动采集 session（多直播间同场）
3. BP 锁定事件 → 切片 G{1}_bp → 规则统计 → 快报（≤2min）→ 完整版（≤10min）同 URL 升级
4. 开局 / 一血 / 团战密度峰值 → 局中切片 → 局中快报 → 局中完整版
5. 小局结束（官方 gameWins / 结算价 ≥0.99 / closed）→ G{n}_end 完整版
6. 整场结束（Polymarket 结算仲裁）→ full 整场复盘（≤15min，全窗口抽样）
7. 比赛结束 → 该场全部节点页转免费公开
8. 情报库沉淀：本场情报资产提炼（选手/队伍/英雄/联赛四维）→ 幂等合并 → 趋势延伸 → 画像页更新
9. 验证回填：弹幕共识 vs 结果、灰信号兑现、BP 锚点应验
10. 历史库收录 + 今日页移除（零点刷新）
```

### 10.2 快报 → 完整版升级

```text
事件触发 → 规则直出快报（硬统计，无语义结论）→ 上线（同 URL）
  → 后台生成完整版（模板 + 溯源）→ 门禁通过 → 同 URL 覆盖
页面始终只有一个 URL；快报期页面标注「速览版 · 完整版跟进」。
```

### 10.3 发布与回滚

```text
reports/（源）→ 全站审计（不通过即停）→ 复制到站点仓库 → 重建今日页/时间轴壳
→ 注入导航/favicon/打点/付费墙 → 提交推送 → Pages 部署（≤1min）
异常时保留上一版站点，问题修复后重新发布。
```

## 12. 监控与运维

### 12.1 自检（self_check）

- 每日：今日清单完整性、节点缺口、结果回填状态、站点审计；
- 输出 runtime/vps_intel/self_check_report.json，问题 TG 告警；
- 空结果必须过自检：禁止报「今日无比赛/无信号」而不告警。

### 12.2 SLA 与成本指标

- 每节点记录：触发 → 快报 → 完整版 → 上线四段时间戳；
- 每页记录 LLM usage（输入/输出 tokens）与成本；
- 日报：覆盖率、SLA 达标率、成本、健康度。

### 12.3 告警规则

- 采集断线 / 0 条数据；
- 节点超时（快报 >2min / 完整版 >10min / 复盘 >15min）；
- 发布失败 / 审计不通过；
- 成本异常（单日 LLM 成本超阈值）；
- 比赛结束但复盘未出（>15min）。

## 13. 质量与防错（四类失效模式）

### 13.1 情报混淆

- 切片硬隔离（联赛源过滤，混源整场作废）；
- 生成门禁（跨联赛/跨场词表扫描）；
- 发布审计（页面 × 联赛 × slug 交叉校验）；
- G5 页面保留依据 = runtime/vps_intel g5 状态文件（不依赖 matches.json 文字比分）。

### 13.2 时效滞后

- SLA 硬承诺 + 事件驱动触发 + 四段时间戳 + 部署压缩（快报同 URL 直上）。

### 13.3 价值下降

- 四步引擎 + LLM 自由提炼 + 保留特殊情报；
- 价值单元双类（持续观点 + 事件反应）；
- 合格标准：「发生了什么 + 意味着什么 + 可溯源」，禁止章节标题/元数据碎片/纯时间线当情报。

### 13.4 格式混乱

- 唯一模板权威（旧 10 段框架）；
- 门禁「每段恰好一次」；
- 发布前全站格式审计。
